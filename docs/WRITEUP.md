# Fighting Dynamic Binary Instrumentation — PoC write-up

## 1. Scope and threat model

The target is the pinned public Linux x86-64 image
`ghcr.io/llaubin/tracer/tracerpin@sha256:cac02a14f9b801e25bf8d7fd992b46371e22d8406d0871de4a9bf0537890c367`.
It contains Intel Pin `3.30-98830-1d7b601b3` and TracerPIN, built from the
public [`llaubin/Tracer` repository (docker branch)](https://github.com/llaubin/Tracer/tree/docker/TracerPIN);
the historical TracerPIN source lineage is additionally available under
`SideChannelMarvels/Tracer`. The image digest is pinned for reproducibility.
The program being protected is intentionally a small dynamically linked C
"hello world".

The objective is narrower than proving that instrumentation is impossible to
hide. The PoC must:

1. distinguish a normal run from the observed TracerPIN run;
2. identify the concrete artifacts on which that distinction depends;
3. test cosmetic attacker changes;
4. explain how an attacker could remove the structural artifacts and what
   sensor should be attempted next.

The kernel is treated as the source of process mappings and descriptors. This
is a useful cost boundary, not an absolute trust boundary: a DBI can instrument
system calls before they reach the kernel or alter the returned application
buffer.

## 2. Reconnaissance

`recon/recon_linux.c` records process identity, thread count, descriptors, and
executable mappings. The same compiled program was run directly and through
TracerPIN.

Several initially plausible channels did not distinguish the runs:

- `TracerPid` was zero after Pin injection because the injector detached;
- the application process still had one thread;
- the signal-context RIP and a normal return address were presented in the
  original application image.

Two repeatable differences remained:

1. Pin created executable anonymous mappings, including its translated code
   cache;
2. Pin and the pintool retained several descriptors in the application’s file
   descriptor table.

The descriptor numbers happened to begin at 128, but the implementation
enumerates the directory rather than relying on that number.

## 3. Implemented sensors

### 3.1 Executable mapping sensor

The detector reads `/proc/self/maps` to EOF using raw `openat`, `read`, and
`close` system calls. It parses each complete line into address range,
permissions, and backing type.

A region votes when it is executable and either:

- has no pathname;
- has a Linux named-anonymous marker (`[anon:...]` or `[anon_shmem:...]`);
- is backed by a memfd.

Testing executable permission rather than simultaneous write and execute
survives the common W^X transition from writable to executable memory.
Recognizing memfd mappings closes a simple file-like code-cache blind spot,
although an ordinary regular-file-backed cache remains indistinguishable from
legitimate executable mappings without additional evidence.

The maps reader deliberately loops to EOF. During review, a single read under
Pin returned only 4,078 bytes from a maps file of approximately 12.6 KB. The
old implementation therefore missed `[stack]` and intermittently crashed in a
stack scanner. The scanner was removed: it added undefined memory traversal
without producing independent evidence against the tested Pin version.

### 3.2 Descriptor sensor

The detector opens `/proc/self/fd`, enumerates it with `getdents64`, and skips
stdio plus its own enumeration descriptor. Every remaining numeric directory
entry is recorded before `readlinkat` is attempted; resolving the target is
only diagnostic and cannot suppress a hit.

A descriptor is not proof of Pin. Launchers, service managers, IDEs, and test
harnesses commonly pass descriptors to children. The policy is consequently:

- one unexpected descriptor is reported but does not vote by itself;
- two or more unexpected descriptors vote;
- any executable mapping hit votes independently.

This threshold matches the observed target, which exposes four descriptors,
but remains heuristic. Two legitimately inherited descriptors can still cause
a false positive.

### 3.3 Address probes that do not vote

The PoC retains two textbook probes because their failure is informative:

- execute `ud2`, catch `SIGILL`, and inspect the saved RIP;
- capture a return address generated by an application call.

On Pin 3.30 both addresses resolve to the original file-backed application
image. Pin is presenting application coordinates even while translated code
executes elsewhere. Both values are printed, but neither changes the verdict.

### 3.4 Error policy

A failed or truncated maps/FD observation is not equivalent to “no artifact”.
The detector therefore uses three outcomes:

| Exit | Meaning |
|---:|---|
| 0 | no voting artifact was observed and both kernel scans completed |
| 1 | the voting policy detected instrumentation artifacts |
| 2 | evidence was unavailable or incomplete |

If one sensor already detects instrumentation, a failure in the other sensor
does not erase that positive result.

## 4. Raw results

The current test image produced the following stable matrix:

| Run | Map hits | FD hits | Result |
|---|---:|---:|---|
| direct execution | 0 | 0 | clean, exit 0 |
| direct execution with one inherited FD | 0 | 1 | clean with ambiguity note, exit 0 |
| stock TracerPIN | 3 | 4 | instrumented, exit 1 |
| cosmetic patched TracerPIN, five consecutive runs | 3 | 4 | instrumented five times, exit 1 |
| executable memfd fixture, backing FD closed | 1 | 0 | instrumented, exit 1 |
| executable regular-file fixture, backing FD closed | 0 | 0 | documented blind spot: clean, exit 0 |
| hundreds of extra mappings plus executable anonymous fixture | at least 1 | 0 | instrumented, exit 1 |
| `/proc` access denied by a seccomp fixture | unavailable | unavailable | inconclusive, exit 2 |

Both stock and patched Pin runs showed file-backed signal and return addresses.
The exact virtual addresses vary under ASLR and are not detection constants.

## 5. Part two: attacker modifications

`lab/patch.sh` makes three changes to the supplied TracerPIN tool:

1. it changes the trace banner;
2. it renames `Tracer.so` and the launcher;
3. it unlinks the trace output immediately after opening it.

The first two changes defeat `lab/naive.c`, which searches maps and the parent
name for `Tracer`. Unlinking removes the trace pathname from the filesystem,
but Linux preserves the open file description and exposes it as a deleted
entry in `/proc/self/fd`.

The structural detector remains positive because these modifications do not
remove Pin’s executable mappings or descriptors. This is a result against a
**cosmetic attacker**, not proof against a modified Pin runtime.

### 5.1 Attacking the actual assumptions

The next attacker must alter the artifacts rather than their labels:

- **Code-cache backing:** use a regular file for translated code and close the
  backing descriptor after `mmap`. Memfd backing is now recognized, but a
  regular executable mapping can blend with application libraries.
- **Trace transport:** send records to an external helper or a pre-established
  shared-memory ring. Pipes and sockets still appear as descriptors; shared
  memory shifts the artifact into the mapping table.
- **Observation forgery:** intercept the raw system calls and edit the maps or
  directory bytes returned to the application. Raw calls bypass a libc-only
  hook, not a DBI’s instruction-level interception.
- **Policy mimicry:** deliberately leave one innocuous-looking descriptor,
  below the current descriptor-only threshold.

A local regression fixture demonstrated the first issue with an executable
memfd mapping. The original empty-path-only parser returned clean after the FD
was closed. The current parser detects memfd backing, but the regular-file
variant remains a documented horizon rather than something hidden by the
report.

## 6. Next experiment: SMC pressure plus calibrated timing

A self-modifying-code (SMC) semantic canary was tested rather than merely
proposed. It emitted `mov eax, 1; ret` into generated code, executed it,
changed the immediate to `2`, and executed it again. Native execution and the
pinned Pin 3.30 image both returned `1` then `2`; the canary did not
distinguish them.

That negative result matches Pin’s documentation: `-smc_support` is enabled by
default, and Pin provides `PIN_SetSmcSupport` and
`TRACE_AddSmcDetectedFunction` for SMC handling. The same documentation warns
that SMC tracking callbacks can cause unbounded memory use. A simple
“translated code must become stale” sensor would therefore be an unjustified
claim and is not added to the detector.

The useful follow-up is a **pressure-and-timing experiment**, not a semantic
oracle:

1. measure distributions for a warmed, repeatedly executed generated block;
2. repeatedly rewrite a randomized set of already translated blocks;
3. measure the rewrite-plus-execute distribution with `RDTSCP`/serialization;
4. compare within-process medians and dispersion rather than one fixed cycle
   threshold;
5. calibrate on bare metal, VMs, loaded systems, and several Pin versions.

Pin must preserve semantics by invalidating/retranslating code or otherwise
coherently executing the new bytes. Repeated randomized rewrites attempt to
amplify that cost. The result remains weak evidence: scheduling, frequency
scaling, virtualization, and a hardened DBI can normalize timing. It should be
a separate weighted sensor alongside mappings and descriptors, never an
infallible verdict.

The AsiaCCS DBI SoK and Arancino work support this layered framing: DBI systems
expose multiple classes of artifacts, while countermeasures can hide
individual environment, code-cache, and timing signals. Coverage across
engines and environments is therefore part of the mechanism, not an
afterthought.

## 7. Limitations

- A legitimate JIT can create the same executable anonymous or memfd mapping.
- Multiple inherited descriptors can satisfy the FD threshold.
- A regular-file-backed cache can evade the current maps classification.
- Pin or a syscall supervisor can forge data even when libc is bypassed.
- The implementation is intentionally Linux x86-64-specific: syscall ABI,
  `ucontext_t` RIP layout, and `ud2` length are architecture-dependent.
- The tested patched pintool does not constitute a hardened Pin runtime.

These are classification limitations, not memory-safety or privilege-boundary
claims. The PoC should be evaluated as one sensor prototype for a larger
coverage-driven protection system.

## 8. Reproduction and coverage

```sh
make
make test

# After building the tracerpin and tracerpin-stealth images:
make test-traced
```

The local suite covers clean execution, one inherited descriptor, executable
memfd backing, the documented regular-file blind spot, a maps file requiring
multiple reads, and unavailable `/proc` evidence. The traced suite runs
the stock image once and the patched image five times to catch intermittent
failures.

For production-style coverage, each test should retain the detector exit code,
raw observations, kernel version, Pin version, image/source revision, and CPU
or virtual-machine identity.

## 9. Development process and AI assistance

AI assistance was used for brainstorming sensors, reviewing C code, and
helping draft documentation. Claims were retained only after source inspection
or execution in the supplied containers.

One initially plausible suggestion was that a call executed from Pin’s code
cache would necessarily leave a code-cache return address on the application
stack. Measurement contradicted it: Pin 3.30 exposed a file-backed application
address. The return-address channel was therefore demoted to non-voting
observational evidence rather than presented as a successful detector.
